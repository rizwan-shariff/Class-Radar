# ClassRadar Auth Implementation Report

## 1. Scope

This report documents the backend Auth work completed for Person 1 (Backend
core), Step 1 of the ClassRadar implementation plan.

The requested Auth scope was:

- `POST /api/v1/auth/login`
- `GET /api/v1/auth/me`
- bcrypt password verification
- JWT tokens valid for 8 hours
- JWT claims: `sub`, `role`, and `sectionId`
- exported `getCurrentUser` helper
- exported `requireRole(...roles)` Fastify pre-handler
- tests covering HTTP 401 and 403 behavior

Only the permitted Auth module directory was changed. No Prisma schema,
OpenAPI contract, web application, timetable module, rooms module, or other
application module was changed.

## 2. Files created

### `apps/api/src/modules/auth/auth.ts`

This is the main Auth implementation.

#### Types

- `AuthRole` defines the supported roles:
  - `STUDENT`
  - `FACULTY`
  - `ADMIN`
- `AuthUser` defines the safe user shape returned to authenticated callers.
  It excludes `passwordHash`.
- `AuthDependencies` defines the minimal database dependency required by the
  module. It exposes a `user.findUnique` method compatible with the Prisma
  User lookup used by the Auth flow.

#### Login validation

The login request body is validated with Zod:

- `email` must be a valid email address.
- `password` must contain at least one character.

Invalid input returns the same generic 401 response as invalid credentials:

```json
{
  "error": {
    "code": "UNAUTHORIZED",
    "message": "Invalid email or password"
  }
}
```

Using one generic response prevents the endpoint from revealing whether an
email address exists.

#### JWT configuration

The JWT secret is read from the `JWT_SECRET` environment variable. The module
throws an explicit configuration error if this variable is missing instead of
using an unsafe fallback secret.

Successful login signs an 8-hour JWT containing:

- `sub`: the authenticated user's ID
- `role`: the user's current role
- `sectionId`: the user's current section ID, or `null`
- `exp`: generated by `jsonwebtoken` from the eight-hour expiry

#### `getCurrentUser`

`getCurrentUser(request, dependencies)`:

1. Reads the `Authorization` header.
2. Requires the `Bearer token` format.
3. Verifies the JWT signature and expiry.
4. Validates the expected claims with Zod.
5. Loads the user by the JWT subject (`sub`).
6. Confirms that the database role and section still match the token.
7. Returns the safe `AuthUser` object without the password hash.

The database lookup and role/section comparison ensure that a validly signed
but stale token cannot silently authorize a user after their role or section
changes.

#### `authPreHandler`

`authPreHandler(dependencies)` is a Fastify pre-handler that calls
`getCurrentUser` and stores the result on `request.authUser`.

Missing, malformed, expired, invalid, or stale credentials return HTTP 401:

```json
{
  "error": {
    "code": "UNAUTHORIZED",
    "message": "Invalid or missing token"
  }
}
```

#### `requireRole`

`requireRole(...roles)` is an exported Fastify pre-handler factory.

- If no authenticated user is present, it returns HTTP 401.
- If the authenticated user's role is not in the supplied role list, it
  returns HTTP 403.
- If the role is allowed, the request continues.

The forbidden response is:

```json
{
  "error": {
    "code": "FORBIDDEN",
    "message": "Insufficient permissions"
  }
}
```

This enforces authorization on the server and does not rely on UI controls.

#### `registerAuthRoutes`

`registerAuthRoutes(app, dependencies)` registers:

- `POST /api/v1/auth/login`
- `GET /api/v1/auth/me`

The login route looks up the user by email, verifies the password with
`bcrypt.compare`, and returns `{ "token": "..." }` on success.

The `/auth/me` route uses `authPreHandler` before returning the authenticated
user profile.

### `apps/api/src/modules/auth/fastify.d.ts`

This file augments Fastify's request type with:

```ts
authUser?: AuthUser
```

The augmentation keeps TypeScript aware of the authenticated user attached by
`authPreHandler`, avoiding unsafe casts in route and authorization code.

### `apps/api/src/modules/auth/auth.test.ts`

This file contains the Auth tests written with Vitest and Fastify's in-memory
`inject` facility.

The bcrypt module is mocked in the test file so the tests remain focused on
route and authorization behavior and do not require a native bcrypt binary
during test execution.

The tests cover:

1. Invalid credentials return HTTP 401 and the expected error shape.
2. Missing authentication on `/auth/me` returns HTTP 401.
3. A valid student JWT attempting to access an admin-only route returns
   HTTP 403 and the expected error shape.

The test dependency is an in-memory `findUnique` implementation. It models
the Prisma lookup contract without requiring a live PostgreSQL database.

## 5. Validation performed

  **passed**

### Blocked check

The requested `pnpm lint && pnpm test` command could not fully pass because:

1. `pnpm lint` fails with `eslint` not recognized. The package script exists,
   but ESLint is not declared or installed in the provided scaffold.
2. The first test attempt was blocked by the native bcrypt binary because
   pnpm ignored dependency build scripts. The Auth tests were then made
   independent of that native binary by mocking bcrypt in the test file, and
   the complete Auth test suite passed.

No application dependency was added and no package manifest was modified.
